# เช็กลิสต์รูปหลักฐานการทดสอบ บทที่ 4

ไฟล์นี้ใช้เป็นรายการงานสำหรับถ่ายภาพประกอบรายงานตั้งแต่หน้า 70 เป็นต้นไป แยกภาพของแอปพลิเคชัน iOS และระบบ Backoffice โดยไม่ต้องนำข้อความทั้งหมดนี้ไปใส่ในเล่ม

## วิธีถ่ายภาพให้ใช้เป็นหลักฐานได้

- ถ่ายให้เห็นชื่อหน้าจอ ข้อมูลที่ใช้ทดสอบ และผลลัพธ์ที่เกิดขึ้นจริง
- งานที่ทำให้ข้อมูลเปลี่ยน เช่น สร้างทริป เข้าร่วมทริป Ban หรือ Approve ควรถ่ายภาพ “ก่อนทำ” และ “หลังทำ”
- ใช้ชื่อผู้ใช้และชื่อทริปชุดเดียวกันทั้งในแอปและ Backoffice เพื่อพิสูจน์ว่าข้อมูลเชื่อมต่อกันจริง
- ปิดบัง JWT Token, API Key, รหัสผ่าน, เลขบัตรประชาชน ที่อยู่ และข้อมูลส่วนบุคคลที่ไม่จำเป็น
- ใต้ภาพในรายงานให้อธิบาย 4 อย่าง: ข้อมูลนำเข้า วิธีทดสอบ ผลที่เกิดขึ้นจริง และผ่าน/ไม่ผ่าน

## หน้า 70 — ผลการเชื่อมต่อ Backend และฐานข้อมูล

### ภาพ 70-1: โครงสร้างการเชื่อมต่อระบบ

- สิ่งที่ต้องทำ: ใช้แผนภาพ `iOS / Backoffice → Backend API → Prisma → PostgreSQL (Supabase)`
- ในภาพต้องเห็น: ชื่อทุกส่วนและลูกศรทิศทางรับ–ส่งข้อมูล
- คำบรรยาย: “ภาพที่ 4.X โครงสร้างการเชื่อมต่อระหว่างแอปพลิเคชัน Backend และฐานข้อมูล”

### ภาพ 70-2: ทดสอบ Login และ JWT

- สิ่งที่ต้องทำ: เรียก Login API ผ่าน Terminal หรือ Postman ด้วยบัญชีทดสอบ
- ในภาพต้องเห็น: URL หรือ endpoint, HTTP Status 200, ข้อมูลผู้ใช้ และช่อง Token ที่ปิดบังค่าแล้ว
- ถ่ายเพิ่มกรณีผิด: รหัสผ่านผิดหรือไม่มี Token และเห็น Status 401/403
- คำบรรยาย: “ภาพที่ 4.X ผลการทดสอบการยืนยันตัวตนด้วย JWT”

### ภาพ 70-3: Backoffice รับข้อมูลจาก Backend

- สิ่งที่ต้องทำ: เปิด Dashboard หรือ User Management หลัง Backend ทำงานแล้ว
- ในภาพต้องเห็น: การ์ดสถิติหรือตารางข้อมูลที่โหลดสำเร็จ ไม่ใช่ข้อมูลตัวอย่างและไม่มี Error
- คำบรรยาย: “ภาพที่ 4.X ผลการรับข้อมูลจาก Backend API มาแสดงในระบบ Backoffice”

## หน้า 71–76 — ระบบ Smart Matching

### ภาพ 71-1: กระบวนการ Smart Matching

- สิ่งที่ต้องทำ: ใช้แผนภาพ `ข้อมูลผู้ใช้ → User Preference Vector → Trip Vector → Cosine Similarity → Match Score → หน้าแอป`
- ในภาพต้องเห็น: ปัจจัย Category 35%, Budget 30%, Activity Style 20% และ Time of Day 15%
- คำบรรยาย: “ภาพที่ 4.X กระบวนการทำงานของระบบ Smart Matching”

### ภาพ 72-1: ข้อมูล User Preference

- หน้าที่ต้องเปิด: หน้าแก้ไขโปรไฟล์หรือแบบสอบถาม User DNA
- ถ่ายอะไร: งบประมาณ ระดับกิจกรรม ช่วงเวลา และหมวดหมู่ที่ผู้ใช้เลือก
- ในภาพต้องเห็น: ค่าที่เลือกครบทั้ง 4 ปัจจัย และใช้บัญชีเดียวกับที่นำไปดู Match Score
- คำบรรยาย: “ภาพที่ 4.X ข้อมูลความต้องการของผู้ใช้ที่ใช้สร้าง User Preference Vector”

### ภาพ 73-1: ข้อมูล Trip Vector

- หน้าที่ต้องเปิด: หน้าสร้างทริปแต่ละขั้นหรือหน้าสรุปก่อนยืนยัน
- ถ่ายอะไร: งบประมาณทริป สไตล์กิจกรรม ช่วงเวลา และหมวดหมู่ทริป
- ในภาพต้องเห็น: จำนวนวัน วันที่เริ่ม–สิ้นสุด และข้อมูล 4 ปัจจัยที่ใช้ Matching
- คำบรรยาย: “ภาพที่ 4.X ข้อมูลคุณลักษณะของทริปที่ใช้สร้าง Trip Vector”

### ภาพ 74-1: ผลคำนวณ Cosine Similarity ใน Terminal

- สิ่งที่ต้องทำ: รัน `test_match_cases.js` หรือชุดทดสอบ Matching ล่าสุด
- ในภาพต้องเห็น: ข้อมูล User, ข้อมูล Trip, Match Score รวม และ breakdown ของ Budget, Activity Style, Category, Time of Day
- ต้องมีอย่างน้อย 3 กรณี: ตรงกันมาก คะแนนสูง / ตรงบางส่วน คะแนนกลาง / แตกต่างมาก คะแนนต่ำ
- คำบรรยาย: “ภาพที่ 4.X ผลการคำนวณ Cosine Similarity และคะแนนแยกรายด้าน”

### ภาพ 74-2: กรณีงบประมาณเกินเงื่อนไข

- สิ่งที่ต้องทำ: ใช้งบประมาณทริปมากกว่างบผู้ใช้เกิน 2 เท่า
- ในภาพต้องเห็น: คะแนน Budget ต่ำตามจริง และ Match Score รวมไม่เกิน 39%
- คำบรรยาย: “ภาพที่ 4.X ผลการใช้กฎจำกัดคะแนนเมื่อทริปเกินงบประมาณผู้ใช้”

### ภาพ 76-1: Match Score บนหน้าแอป

- หน้าที่ต้องเปิด: หน้าแนะนำหรือค้นหาทริป
- ถ่ายอะไร: การ์ดทริปที่มีคำว่า “เข้ากันได้ X%”
- แนะนำ: ทำให้เห็นอย่างน้อย 3 ระดับในภาพเดียว ได้แก่ คะแนนสูง ปานกลาง และต่ำ
- ห้ามใช้ภาพที่ทุกทริปเป็น 0% เพื่อสรุปว่าระบบ Matching ทำงานสมบูรณ์
- คำบรรยาย: “ภาพที่ 4.X การแสดงและจัดลำดับทริปตาม Match Score”

### ภาพ 76-2: คะแนนย่อยในหน้ารายละเอียด

- หน้าที่ต้องเปิด: Trip Detail ของทริปเดียวกับภาพหน้าแนะนำ
- ในภาพต้องเห็น: คะแนนรวม และเปอร์เซ็นต์ Budget, Activity Style, Category, Time of Day
- ตรวจให้คะแนนด้านขวาสอดคล้องกับข้อมูลจริง ไม่ใช่คะแนนรวมถูกจำกัดแต่ Budget ยังแสดงสูงผิดจริง
- คำบรรยาย: “ภาพที่ 4.X การแสดง Match Score และรายละเอียดความเข้ากันได้รายด้าน”

## หน้า 77 — Unit Testing

### ภาพ 77-1: ผล Unit Test ของ Matching

- โปรแกรมที่ใช้: Terminal ใน VS Code
- คำสั่ง: รันไฟล์ทดสอบ Matching ของ Backend
- ในภาพต้องเห็น: ชื่อกรณีทดสอบ ผลคะแนนแต่ละกรณี และข้อความสรุปว่าทดสอบผ่าน
- กรณีที่ควรมี: ตรงทุกด้าน, ตรงบางด้าน, งบต่างมาก, กิจกรรมต่างมาก, Category ไม่ตรง, เวลาไม่ตรง และไม่ตรงทุกด้าน
- คำบรรยาย: “ภาพที่ 4.X ผลการทดสอบฟังก์ชันคำนวณ Match Score”

## หน้า 78–79 — Integration Testing

- ภาพหลังฝั่ง Backoffice: ค้นพบชื่อทริปเดียวกัน พร้อมชื่อผู้สร้าง วันที่ และงบประมาณตรงกัน
- คำบรรยาย: “ภาพที่ 4.X ผลการทดสอบ App → API → Database ในกระบวนการสร้างทริป”

### ภาพ 78-2: Matching API

## หน้า 80–81 — System Testing แบบ Black Box

### ST-01 สมัครสมาชิกสำเร็จ

- หน้าที่ต้องถ่าย: หน้าสมัครสมาชิกและหน้าหลังสมัครสำเร็จ
- ต้องเห็น: Username/Email ที่ใช้ทดสอบ และผลว่าระบบเข้าสู่ขั้นต่อไปได้

### ST-02 สมัครสมาชิกไม่สำเร็จ

- หน้าที่ต้องถ่าย: หน้าสมัครที่กรอกข้อมูลไม่ครบหรือใช้อีเมลซ้ำ
- ต้องเห็น: ข้อความแจ้งข้อผิดพลาดที่เข้าใจได้

### ST-03 บันทึก User DNA

- หน้าที่ต้องถ่าย: หน้าแบบสอบถามหรือหน้าแก้ไขสไตล์การเดินทางหลังเลือกข้อมูล
- ต้องเห็น: งบประมาณ กิจกรรม ช่วงเวลา และความสนใจครบ

### ST-04 สร้างทริป

- หน้าที่ต้องถ่าย: หน้าสรุปก่อนสร้าง และหน้า “ทริปของฉัน” หลังสร้าง
- ต้องเห็น: ชื่อทริปเดียวกันและผู้สร้างเป็นบัญชีที่กำลังใช้งาน

### ST-05 แสดงและเรียง Match Score

- หน้าที่ต้องถ่าย: หน้าแนะนำทริป
- ต้องเห็น: คะแนนหลายระดับและลำดับคะแนนจากมากไปน้อย

### ST-06 เข้าร่วมทริปสำเร็จ

- หน้าที่ต้องถ่าย: Trip Detail ก่อนและหลังเข้าร่วม
- ต้องเห็น: ปุ่มหรือสถานะเปลี่ยน และจำนวนสมาชิกเพิ่มขึ้น

### ST-07 ทริปเต็ม

- หน้าที่ต้องถ่าย: Trip Detail ของทริปที่สมาชิกครบ
- ต้องเห็น: ระบบไม่อนุญาตให้เข้าร่วมและมีข้อความอธิบาย

### ST-08 ออกจากทริป

- หน้าที่ต้องถ่าย: ก่อนและหลังออกจากทริป
- ต้องเห็น: รายชื่อสมาชิกหรือจำนวนผู้เข้าร่วมลดลง

### ST-09 ห้องแชตกลุ่ม

- หน้าที่ต้องถ่าย: Group Chat ของสมาชิกสองบัญชี
- ต้องเห็น: ชื่อผู้ส่ง เวลา และข้อความที่ส่ง–รับสำเร็จ
- ห้ามใช้หน้า AI Chat แทน Group Chat

### ST-10 ทริปหมดอายุ

- หน้าที่ต้องถ่าย: Trip Detail ของทริปที่วันสิ้นสุดผ่านแล้ว
- ต้องเห็น: เข้าร่วมไม่ได้ และ Match Score เป็น 0 ตามเงื่อนไขระบบ

## รูปทดสอบ Backoffice ที่ต้องถ่ายเพิ่ม

### BO-01 Dashboard

- ถ่ายหน้า: Backoffice Dashboard
- ต้องเห็น: จำนวนผู้ใช้ ทริป คำขอยืนยันตัวตน รายงาน บัญชียืนยันแล้ว และบัญชีถูกระงับ
- ตรวจ: ตัวเลขควรสัมพันธ์กับรายการจริงที่เปิดดูได้

### BO-02 User Management

- ภาพที่ 1: ตารางผู้ใช้และผลการค้นหาด้วยชื่อหรืออีเมล
- ภาพที่ 2: ก่อน Ban โดยสถานะเป็นใช้งานปกติ
- ภาพที่ 3: หลัง Ban โดยสถานะเปลี่ยนเป็นระงับ
- ถ้าทดสอบ Unban ให้ถ่ายสถานะหลังปลดระงับอีกหนึ่งภาพ
- คำบรรยาย: “ภาพที่ 4.X ผลการค้นหาและจัดการสถานะผู้ใช้”

### BO-03 Trip Management

- ภาพที่ 1: ผลค้นหาด้วยชื่อทริป ปลายทาง หรือชื่อผู้สร้าง
- ภาพที่ 2: รายละเอียดทริปที่เห็นผู้สร้าง วันที่ งบประมาณ สมาชิก Category และ Itinerary
- หากทดสอบ Delete ให้สร้างทริปทดสอบเฉพาะ ห้ามลบทริปจริง และถ่ายก่อน–หลังลบ
- คำบรรยาย: “ภาพที่ 4.X ผลการตรวจสอบและจัดการข้อมูลทริป”

### BO-04 User Reports

- ภาพที่ 1: รายการที่เห็น Reporter, Reported User, Reason, เวลา และสถานะ
- ภาพที่ 2: หลังดำเนินการ Warn หรือ Ban
- ต้องตรวจในแอปผู้ใช้ด้วยว่าได้รับคำเตือนหรือสถานะถูกเปลี่ยนจริง
- คำบรรยาย: “ภาพที่ 4.X ผลการจัดการรายงานผู้ใช้”

### BO-05 Identity Verification

- ภาพฝั่งแอป: ส่งคำขอแล้วเป็นสถานะรอตรวจสอบ
- ภาพฝั่ง Backoffice: เห็น Face Scan และเอกสารสำหรับเปรียบเทียบ
- ภาพหลังดำเนินการ: Approve หรือ Reject และสถานะเปลี่ยน
- ภาพกลับฝั่งแอป: ผู้ใช้เห็น Verified Badge หรือข้อความปฏิเสธ
- ต้องปิดบังเลขเอกสารและข้อมูลส่วนตัว
- คำบรรยาย: “ภาพที่ 4.X ผลการตรวจสอบและเปลี่ยนสถานะการยืนยันตัวตน”

### BO-06 System Alerts & Notifications

- ภาพที่ 1: ฟอร์มสร้างประกาศที่กรอก Title, Message และประเภทแล้ว
- ภาพที่ 2: ประกาศปรากฏในประวัติหลังส่ง
- ภาพที่ 3: ข้อความเดียวกันปรากฏในหน้าแจ้งเตือนของแอปผู้ใช้
- คำบรรยาย: “ภาพที่ 4.X ผลการส่งประกาศจาก Backoffice ไปยังแอปพลิเคชัน”

## หน้า 82 เป็นต้นไป — UAT, SUS และ Performance

### UAT

- ถ่ายผู้ทดสอบกำลังทำภารกิจได้ 1–2 ภาพโดยขออนุญาตก่อน และไม่ต้องเห็นใบหน้าหากไม่จำเป็น
- หลักฐานสำคัญกว่ารูปคือ ตารางจำนวนผู้ทดสอบ ผ่าน ไม่ผ่าน ปัญหาที่พบ และอัตราสำเร็จ
- ห้ามกรอกตัวเลขสมมติ ต้องใช้ผลจากผู้ทดสอบจริง

### SUS

- ถ่ายแบบสอบถามหรือสรุปคำตอบโดยไม่เปิดเผยชื่อผู้ตอบ
- ทำกราฟคะแนนรายข้อและคะแนน SUS รวม
- ต้องระบุจำนวนผู้ตอบและวิธีคำนวณคะแนน

### Performance Testing

- ทดสอบอย่างน้อย 3 ครั้งต่อรายการ: โหลด Feed, โหลด Trip Detail, Matching API และ Generate Itinerary
- ภาพต้องเห็น Response Time หรือเวลาเริ่ม–สิ้นสุดจาก Terminal/Postman/Log
- บันทึกค่าครั้งที่ 1–3 และค่าเฉลี่ยลงตาราง
- ถ้าบทที่ 3 ไม่ได้กำหนดเกณฑ์เวลา ให้รายงานว่าเป็น “ผลการวัด” และไม่สรุปผ่าน/ไม่ผ่านโดยสร้างเกณฑ์ย้อนหลัง

## ลำดับถ่ายภาพที่ทำงานง่ายที่สุด

1. สร้างบัญชีทดสอบ User A และ User B
2. บันทึก User DNA ของทั้งสองบัญชี
3. ให้ User A สร้างทริป และตรวจใน My Trips กับ Backoffice
4. ให้ User B เปิดหน้าแนะนำและ Trip Detail เพื่อถ่าย Match Score
5. ให้ User B เข้าร่วมทริป แล้วตรวจจำนวนสมาชิกทั้งแอปและ Backoffice
6. ใช้ User A และ User B ส่งข้อความใน Group Chat
7. ส่งคำขอยืนยันตัวตนจากแอป แล้ว Approve/Reject ใน Backoffice
8. สร้างประกาศใน Backoffice แล้วตรวจหน้าแจ้งเตือนในแอป
9. ทดสอบ Ban/Unban ด้วยบัญชีทดสอบ
10. รัน Unit Test, API Test และ Performance Test ใน Terminal แล้วเก็บภาพผลลัพธ์
