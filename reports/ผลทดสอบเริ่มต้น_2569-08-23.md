### Trips API

```text
GET /api/trips
HTTP status = 200

```

ผลครั้งนี้แสดงว่า endpoint ใช้งานได้ แต่เวลาตอบสนองของรายการทริปสูงกว่า Root API อย่างชัดเจน ควรทดสอบซ้ำอย่างน้อย 3 ครั้งก่อนคำนวณค่าเฉลี่ยและนำไปสรุปในหัวข้อ Performance Testing

## ข้อสังเกตสำคัญ

1. ไฟล์ทดสอบปัจจุบันเป็นสคริปต์พิมพ์ผลลัพธ์ ยังไม่มี `assert` หรือ Test Runner ที่ตัดสินผ่าน/ไม่ผ่านอัตโนมัติ สถานะในตารางจึงพิจารณาจากผลลัพธ์เทียบกับเงื่อนไขที่กำหนด
2. คำเตือน `Firebase Admin config not found` ไม่ทำให้การคำนวณ Matching ล้มเหลว แต่หมายความว่าสภาพแวดล้อมที่รันทดสอบนี้ยังทดสอบ Push Notification ไม่ได้
3. ค่า Category ที่เป็น `null` หมายถึงไม่มีข้อมูลที่ระบบใช้คำนวณ ไม่ควรตีความเป็น 0% เพราะ 0% หมายถึงมีข้อมูลทั้งสองฝั่งแต่ไม่ตรงกัน
4. ผลเวลา Response เป็นการวัดครั้งเดียว ยังไม่เพียงพอสำหรับสรุปประสิทธิภาพสุดท้าย

## งานทดสอบลำดับถัดไป

- วัด Root API และ Trips API อย่างละ 3 ครั้งแล้วหาค่าเฉลี่ย
- ทดสอบ Login สำเร็จ/รหัสผิด/ไม่มี Token โดยปิดบัง Token ในหลักฐาน
- ทดสอบสร้างทริปผ่านบัญชีผู้ใช้และตรวจว่าปรากฏใน My Trips กับ Backoffice
- ทดสอบเข้าร่วมทริป ทริปเต็ม ทริปหมดอายุ และออกจากทริป
- ทดสอบ Group Chat ด้วยผู้ใช้สองบัญชี
- ทดสอบ Backoffice: Ban/Unban, Reports, Verification และ System Notification

### ข้อบกพร่อง/ข้อสังเกตที่พบ

1. ทริปชื่อ “สักที่” แสดงวันเริ่มต้นเป็น `5/10/2548` ซึ่งเป็นวันที่ในอดีตและผิดปกติ ควรตรวจ validation วันที่ตอนสร้างทริปและข้อมูลเดิมในฐานข้อมูล
2. หน้ารายงานผู้ใช้ หน้ายืนยันตัวตน และหน้าแจ้งเตือนมีโครงสร้างหน้าตา/เมนูไม่เหมือน Dashboard, Users และ Trips เนื่องจากไม่แสดง Sidebar หลังบ้าน จึงควรปรับ Layout ให้เป็นรูปแบบเดียวกัน
3. ประวัติแจ้งเตือนมีรายการซ้ำจำนวนมาก เช่น การเข้าร่วมทริปเดียวกันโดยผู้ใช้เดียวกันหลายครั้ง ควรตรวจการสร้าง Notification ซ้ำหรือเพิ่มกลไกป้องกัน Duplicate Event
4. การทดสอบครั้งนี้ยังไม่ทดสอบการเปลี่ยนสถานะจริง เพราะ Ban, Delete, Approve/Reject, Send Alert และ Clear All เป็นการแก้ไขข้อมูลจริง ควรใช้บัญชีและข้อมูลสำหรับทดสอบโดยเฉพาะก่อนดำเนินการ
